# План реализации трёх режимов подбора

> **Заменён уточнением владельца 17.11.2026. Не исполнять буквально.** Теперь два режима и полезность уточнений без жёсткого cap шесть: [актуальный проект решения](../specs/2026-11-17-two-selection-modes-design.md), [ROADMAP](../../../ROADMAP.md). После согласования нужен новый адресный план; пути и старые проверки можно переиспользовать после сверки. Три карточки, 2/4/6, автоматический neutral-stop и матрица 4×3×2 больше не являются актуальным заданием.

> Для исполнителя: после отдельного поручения на разработку использовать `executing-plans` для последовательной работы. Агентный способ требует применимых инструкций или отдельного выбора владельца. Этот файл сам не запускает исполнение, коммиты или публикацию.

**Статус:** запланировано 12.11.2026; все пункты исполнения не выполнены.

**Цель:** человек выбирает объём разговора в любом из четырёх разделов, управляет его продолжением и видит выбранный режим в сохранённом подборе.

**Архитектура:** один общий контракт глубины и общая политика ограничений поверх двух существующих conversation-ядер. Текущие entry/client/archive/library/feedback расширяются, без параллельной системы диалога. `guided/free` и API reasoning effort остаются отдельными настройками.

**Стек:** vanilla JavaScript ES modules, Node, существующий Build Output API и browser storage. Новые зависимости не требуются.

**Спецификация:** [проект решения и основания](../specs/2026-11-12-selection-depth-design.md). Читать целиком до исполнения, особенно правила подсчёта, legacy и запрет приписывать минутам измеренную точность.

## Общие ограничения

- Только игры/фильмы/сериалы/мультфильмы modern; legacy не мигрировать.
- Потолки дополнительных вопросов `quick=2`, `standard=4`, `deep=6`, обязательного минимума нет. Базовые game platform/company/party из ядра вне этого бюджета, но входят в полное время и видимое объяснение нагрузки. Число результатов до четырёх одинаково, модель/effort/поиск/каталог не менять ради режимов.
- Сохранить v3-черновики первого вопроса и общую фабрику; архив/restore/reload не вызывают AI.
- `alreadyShown` не становится dislike; планы, знакомство, вкус и глубина остаются разными данными.
- Совместимость с прежними pending/error/result snapshots; поле глубины отсутствует → legacy, не quick.
- Бесплатные проверки: отдельный QA origin, подменённый транспорт/AI off, отключённая рабочая БД. Никаких пользовательских journals/ledger в fixtures или bundle.
- Будущий платный опыт: актуальный ledger/receipts/lock, учёт unresolved, отдельные dispatch/cap/stop и фактический расход. Текущий план не расходует прежний грант.
- Hosted-изменения только TASTIQ в разрешённом Family, с отдельным ingestion token; перед работой с Supabase прочитать его актуальный skill/runbook. Push и deploy — отдельные действия по поручению.
- Другие чаты меняют файлы продукта. Перед каждой записью сверить актуальный diff; не отменять и не включать их изменения в свою работу.

## На что обратить внимание при проверке

1. Короткий режим не превращает неизвестное условие в подтверждённое и не ухудшается намеренно.
2. Back, retry, смена вопроса, поправка и переключение режима не обходят потолок и не теряют уже написанное.
3. Старый сохранённый подбор не получает выдуманный режим и открывается без AI.
4. Библиотека и отправленный feedback описывают режим данной выдачи, а не последние настройки браузера.
5. Время и качество не оцениваются только по довольным/завершившим; пользовательский выбор режима не выдаётся за A/B-эксперимент.
